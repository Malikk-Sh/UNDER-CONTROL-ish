# Всё под контролем! · UNDER CONTROL-ish

Кооперативный 2D-платформер для браузера и телефона: бригада сомнительно
квалифицированных работников чинит, носит и запускает оборудование в опасном
комплексе — и создаёт новые проблемы быстрее, чем решает старые.

Реализация MVP по [техническому GDD](./Under_Control_GDD_AI_RU.md): свободное
независимое движение, кооперация без фиксированного состава (1–8 игроков,
стресс-тест до 12), авторитетный сервер с предсказанием на клиенте, обучающий
шлюз, три рабочие зоны и финальная эвакуация.

## Быстрый старт

```bash
npm install
npm run dev            # сервер :2567 и клиент :5173 одновременно
```

Откройте <http://localhost:5173>, нажмите «Найти смену». Чтобы позвать друзей —
«Создать приватную» и продиктуйте код из четырёх букв.

Продакшен-сборка одной командой:

```bash
npm run build          # собирает клиент в apps/client/dist
npm start              # сервер раздаёт и статику, и WebSocket на одном порту
```

## Управление

| Действие               | Клавиатура        | Геймпад       | Сенсор                        |
|------------------------|-------------------|---------------|-------------------------------|
| Движение               | `A` / `D`, стрелки| Левый стик    | Плавающий стик слева          |
| Прыжок                 | `Space`           | A / Cross     | Кнопка «Прыжок»               |
| Взять / использовать   | `E` (удерживать)  | X / Square    | Кнопка «Взять»                |
| Бросить                | `F`               | B / Circle    | «Бросок» + свайп для прицела  |
| Подкат                 | `S` / `Ctrl` / `↓`| Bumper        | Свайп вниз по стику           |
| Метка                  | `Q`               | D-pad         | Кнопка «Метка»                |

Отпускание `E` аккуратно кладёт предмет, `F` — швыряет. В настройках есть
«режим без удерживания», который превращает `E` в переключатель — на телефоне
это обязательный режим, потому что палец нужен ещё и стику.

## Что уже работает

- **Свободное движение** с coyote time, буфером прыжка, подкатом и мягкими
  столкновениями игроков: толкнуть можно, перекрыть проход — нет.
- **Совместный перенос**: тяжёлый груз соло тащится втрое медленнее, вдвоём —
  почти на полной скорости; соло-путь есть всегда.
- **Масштабирование под состав**: число активаторов считается как
  `max(1, min(3, ceil(N × 0,4)))`, интенсивность опасностей растёт логарифмически
  и упирается в потолок, у малого состава меньше узлов ремонта и длиннее окна.
- **Опасности по правилу трёх фаз**: предупреждение → удар → гарантированное
  окно. Прессы, магниты, электризованная вода, струи пара, конвейеры.
- **Гарантия ключевых предметов**: упавший в кислоту или за карту груз
  возвращается на точку восстановления, повреждения частично откатываются.
- **Спасение товарищей** с убывающей отдачей от числа помощников и
  автоматическим возвращением в игру не дольше чем через пять секунд.
- **Директор хаоса**, выбирающий только заранее подготовленные вариации.
- **Drop-in / drop-out** и переподключение в течение 45 секунд.
- **Мобильный UX**: safe-area, ландшафт, полноэкранный режим, PWA, раскладка
  для левшей, регулировка тряски, вспышек и частиц, субтитры звуков.

## Архитектура

```text
packages/shared/     общие правила: симуляция, протокол, контент, настройки
  src/sim/           детерминированная физика, игрок, предметы, устройства, мир
  src/content/       комнаты в виде данных (ASCII-геометрия + сущности)
  src/config/        числовые параметры и формулы масштабирования
  src/protocol/      сообщения и зеркало синхронизируемого состояния
apps/server/         авторитетный Colyseus: комната, схема, директора, валидация
apps/client/         Phaser: сцены, рендер, ввод, звук, интерфейс
packages/tools/      валидатор уровней и дымовые тесты
tests/               автотесты симуляции, формул, опасностей и контента
```

Ключевое решение — **общий пакет правил**. `stepPlayerMotion` физически один и
тот же код на сервере и на клиенте, поэтому предсказание совпадает с
авторитетной симуляцией, а не «примерно повторяет» её.

### Сеть

| Данные            | Авторитет | Как передаётся                        |
|-------------------|-----------|---------------------------------------|
| Ввод игрока       | клиент → проверка сервером | 30 пакетов/с, sequence ID |
| Положение игроков | сервер    | 20 снимков/с + интерполяция на 110 мс |
| Ключевые предметы | сервер    | состояние + события захвата           |
| Опасности         | сервер    | параметры один раз, фаза считается от времени |
| Частицы, звук     | клиент    | не синхронизируются вовсе             |

Локальный персонаж предсказывается сразу, при расхождении клиент возвращается
на серверную позицию и переигрывает неподтверждённый ввод. Захват предметов
намеренно **не** предсказывается: владельца назначает только сервер, иначе
ключевой предмет начнёт двоиться.

### Отклонения от GDD

GDD §17.1 рекомендует Matter.js. Вместо него написана собственная
детерминированная AABB-симуляция в `packages/shared/src/sim`. Причина: та же
физика должна исполняться на сервере авторитетно и на клиенте для предсказания,
с побитово одинаковым результатом и возможностью переигрывать прошлые кадры.
Matter.js для reconciliation пришлось бы полностью сериализовать и откатывать
каждый тик. Раздел §0.4 такую замену разрешает: 2D web, серверная авторитетность
и мобильная поддержка сохранены. Остальной стек — TypeScript, Phaser, Node.js,
Colyseus, Vite, Vitest — взят как рекомендовано.

## Ассеты

Внешних файлов графики и звука в проекте нет. Спрайты рисуются в canvas при
загрузке (`apps/client/src/art/textures.ts`), звук синтезируется через Web Audio
(`apps/client/src/audio/AudioSystem.ts`), иконки PWA собираются самописным
PNG-энкодером (`apps/client/scripts/make-icons.mjs`, запуск `npm run icons -w @uc/client`).
Игра стартует мгновенно и одинаково выглядит везде, а палитра меняется в одном файле.

## Контент

Комната — это данные: ASCII-сетка геометрии плюс список сущностей в тайловых
координатах. Символы карты: `#` стена, `=` настил (проходим снизу), `~` вода,
`!` кислота, `*` лёд, `.` пусто.

```bash
npm run validate:levels                       # проверить все комнаты
npm run validate -w @uc/tools -- --map factory_hot_delivery   # печать карты с линейкой
```

Валидатор проверяет вход, выход, чекпоинт и резервное решение, прогоняет
симуляцию на составах 1/2/4/8/12, сверяет число активаторов, ищет опасности без
телеграфирования и висящие сигналы. Он же запускается в тестах, поэтому
сломанная комната не доедет до плейтеста.

## Тесты

```bash
npm run typecheck      # tsc -b по всем пакетам
npm test               # 108 автотестов: формулы, движение, опасности, контент
npm run validate:levels

# сквозные проверки на живом сервере
npm start &
npm run smoke -w @uc/tools -- ws://localhost:2567 3 5     # три бота по сети
npx tsx --tsconfig packages/tools/tsconfig.json \
    packages/tools/src/cli-browser-smoke.ts http://localhost:2567 shot.png
```

Браузерный тест открывает настоящий Chromium, входит в смену, нажимает реальные
клавиши и проверяет, что персонаж поехал: это ловит то, что не видно юнит-тестам —
инициализацию Phaser, генерацию текстур и связку предсказания с сетью.

## Деплой на render.com

В корне лежит [`render.yaml`](./render.yaml). В панели Render: **New → Blueprint**,
указать репозиторий — сервис создастся сам.

Один web service делает всё: собирает клиент и поднимает Colyseus, который
раздаёт статику и принимает WebSocket на том же `$PORT`. Отдельный static site
не нужен — игровой сокет должен жить на том же origin.

Особенности:

- `buildCommand` содержит `npm ci --include=dev`: Render выставляет
  `NODE_ENV=production`, из-за чего npm иначе пропустит Vite и сборка упадёт;
- health check настроен на `/healthz`;
- симуляция идёт в одном процессе, поэтому `numInstances: 1`. Горизонтальное
  масштабирование потребует общего presence-слоя (Redis).

## Ограничения MVP

Осознанно не реализовано (GDD §19.3): открытый мир, редактор уровней, классы и
дерево навыков, PvP, голосовой чат, процедурная геометрия, магазин и аккаунтная
экономика. Из биомов сделан только сортировочный завод; затопленная лаборатория,
воздушный терминал и тепловая станция описаны в GDD, но не собраны.

Прогрессия между сменами не сохраняется: PostgreSQL по плану GDD появляется
позже, сейчас итоги показываются на экране результатов и на этом заканчиваются.
